## 1.1 数据库导论 (Introduction)

### 核心概念定义（必背）

| 术语 | 定义 | 页码 |
|---|---|---|
| 数据 (Data) | 为参考或分析而收集的事实与统计 | [1.1 p14] |
| 数据库 (Database) | 一个**共享的、逻辑相关的数据集合（及对数据的描述）**，为满足组织的信息需求而设计 | [1.1 p14] |
| 系统目录/元数据 (System catalogue / metadata) | 对数据的描述，用于实现**程序-数据独立性 (program–data independence)** | [1.1 p14] |
| DBMS | 使用户能够**定义 (define)、创建 (create)、维护 (maintain)、控制访问 (control access)** 数据库的软件系统 | [1.1 p16] |
| 数据库应用程序 (Application program) | 与数据库交互、向 DBMS 发出请求（如 SQL）的程序 | [1.1 p16] |
| 数据模型 (Data model) | 对“现实世界”对象、事件及其关联的表示 | [1.1 p17] |
| 模式 vs 数据 (Schema vs Data) | **Schema** = 数据库的描述（结构）；**Data** = 实际存储的信息 | [1.1 p17] |

- **逻辑相关数据三要素**：实体 (Entity，组织中要表示的独立对象)、属性 (Attribute，描述对象某方面的性质)、关系 (Relationship，实体间的关联)。`[1.1 p15]`

### 数据库环境中的角色 (Roles) `[1.1 p19]`
- 数据管理员 (Data Administrator, DA)
- 数据库管理员 (Database Administrator, DBA)
- 数据库设计师 (Designers：逻辑 Logical / 物理 Physical)
- 应用开发者 (Application Developers)
- 终端用户 (End Users：初级 naive / 高级 sophisticated)

### 三级 ANSI-SPARC 体系结构 (Three-level ANSI-SPARC architecture) ★高频考点 `[1.1 p20-22]`

| 层级 | 内容 |
|---|---|
| 外部层 (External level) | 各用户的视图 (View 1…View n)，每个用户看到定制化的数据 |
| 概念层 (Conceptual level) | 概念模式 (Conceptual Schema)，整个数据库的逻辑结构 |
| 内部层 (Internal level) | 内部模式 (Internal Schema)，数据的物理存储组织 |

- **目的 (Objective)**：将**每个用户的视图**与数据库的**物理表示方式**分离。`[1.1 p21]`
- 由此带来的好处（常考论述）：
  - 用户能以定制视图访问数据；修改某用户视图不影响其他用户。`[1.1 p21]`
  - 用户无需处理物理存储细节（与存储无关，**数据独立性**）。`[1.1 p21]`
  - 物理存储变化不影响用户视图与数据库内部结构。`[1.1 p22]`
  - DBA 可在最小影响用户视图的前提下改变概念结构。`[1.1 p22]`

### DBMS 发展史 (History) `[1.1 p23-24]`
- 60s 早期：Charles Bachman → 网状数据模型 (Network Data Model)、CODASYL、IDS。
- 60s 晚期：IBM IMS → 层次数据模型 (Hierarchical Data Model)。
- 70s：**Edgar F. Codd (IBM, 图灵奖 1981)** 提出**关系数据模型 (Relational Data Model)**。
- 80s：关系模型、SQL 标准、事务管理 (James Gray, 图灵奖 1999)。
- 90s：Web 访问、多媒体数据、面向对象数据模型。
- 2000+：数据仓库与数据挖掘、NoSQL、大数据、云数据库。
- **关键结论**：目前关系型数据库仍是使用最广泛的数据库技术。`[1.1 p24]`

## 1.2 关系模型与关系代数 (Relational Model & Relational Algebra)

### A. 关系模型术语 (Terminology) ★必背 `[1.2 p5-7]`

- 关系模型由 **E. F. Codd 于 1970 年**提出；数据全部逻辑化地组织在**关系/表 (relations/tables)** 中。`[1.2 p5]`

| 术语 | 含义 |
|---|---|
| 关系 (Relation) | 由行和列组成的表 |
| 属性 (Attribute) | 关系中命名的列 (named column) |
| 元组 (Tuple) | 关系中的一行 (row) |
| 域 (Domain) | 一个或多个属性允许取值的集合 (set of allowable values) |
| 度 (Degree) | 关系中**属性（列）的数量** |
| 基数 (Cardinality) | 关系中**元组（行）的数量** |
| 关系数据库 (Relational database) | 具有不同名称的规范化关系的集合 |

### B. 关系的性质 (Properties of relations) `[1.2 p10]`
- 关系名在模式中唯一。
- **每个单元格只含一个原子（单一）值** → 第一范式 (First Normal Form)。
- 每个属性名唯一；同一属性的值来自同一个域。
- **元组不重复**（无重复行）。
- 属性顺序无意义；元组顺序（理论上）无意义。

### C. 关系键 (Relational Keys) ★必考 `[1.2 p11-13]`

| 键 | 定义 | 判据 |
|---|---|---|
| 候选键 (Candidate Key) | 能唯一标识元组的属性集 | **唯一性 (Uniqueness)** + **不可约性 (Irreducibility，无任何真子集仍具唯一性)** |
| 主键 (Primary Key) | 被选作唯一标识元组的候选键 | 从候选键中选一个 |
| 外键 (Foreign Key) | 一个关系中匹配**另一个（或同一）关系候选键**的属性集 | 用于连接关系 |
| 复合键 (Composite Key) | 由两个或以上属性组成的候选键 | 见 [1.3 p20] |

> **易错点**：候选键必须同时满足唯一性**和**不可约性；只满足唯一性而可约的不是候选键。

### D. 关系模式表示法 (Relational Schema) `[1.2 p14-15]`
- 格式：`关系名(属性1, 属性2, …, 属性n)`，主键通常加下划线。
- 例：`Branch(branchNo, street, city, postcode)`、`Client(clientNo, fName, lName, telNo, prefType, maxRent)`。

### E. 完整性约束 (Integrity Constraints) ★必考 `[1.2 p16-17]`
- **空值 (Null)**：表示当前未知或不适用的值；**≠ 0、≠ 空格**（0 和空格是值）。
- **实体完整性 (Entity Integrity)**：基本关系中，**主键的任何属性都不能为 null**。
- **参照完整性 (Referential Integrity)**：若存在外键，则外键值要么**匹配其宿主关系 (home relation) 中某元组的候选键值**，要么为 null。
- **一般约束 (General Constraints)**：对值的具体限制，如 `0 < 身高(cm) < 250`。

### F. 关系代数 (Relational Algebra) ★核心计算考点

- 关系代数是与关系模型关联的**形式语言**；操作作用于一个或多个关系，**产生新关系而不改变原关系**。`[1.2 p20]`
- **闭包性质 (Closure)**：结果仍是关系，故表达式可嵌套（如算术）。`[1.2 p20]`
- 基本操作：选择、投影、笛卡尔积、连接；集合操作：并、差、交。`[1.2 p21]`

#### 一元操作

**① 选择 σ (Selection)** `[1.2 p22-25]`
- `σ_condition(R)`：返回 R 中**满足条件的行（水平子集）**。
- 例：`σ_salary>10000(Staff)`；`σ_salary>10000 ∧ sex='F'(Staff)`；`σ_city='London'(Branch)`。

**② 投影 π (Projection)** `[1.2 p26-28]`
- `π_col1,…,coln(R)`：返回指定列的**垂直子集，并去除重复**。
- 例：`π_staffNo,fName,lName,salary(Staff)`；`π_city(Branch)`。

**选择 + 投影组合**（注意操作顺序）`[1.2 p29]`
- 列出 salary>20000 的 staffNo、position、salary：
  `π_staffNo,position,salary(σ_salary>20000(Staff))`
- 列出伦敦分行的 branchNo：`π_branchNo(σ_city='London'(Branch))`。
> **易错点**：先选择再投影；若投影列里不含选择条件用到的列，必须先做选择。

#### 二元 / 连接操作

**③ 笛卡尔积 × (Cartesian product)** `[1.2 p30-31]`
- `R × S`：R 每个元组与 S 每个元组拼接。
- 结果**度 = deg(R)+deg(S)**，**基数 = card(R)×card(S)**。

**④ 连接 Join** `[1.2 p32-36]`
- 连接是笛卡尔积的派生：相当于在 `R × S` 上用连接条件做选择。
- **自然连接 (Natural Join) `R ⋈ S`**：在**公共属性上相等**的所有元组组合（公共列只保留一份）。`[1.2 p33-34]`
- **θ 连接 (Theta join) `R ⋈_F S`**：含满足条件 F 的笛卡尔积元组；可改写为 `σ_F(R × S)`。`[1.2 p36]`
- 例：`π_staffNo(σ_city='London'(Staff ⋈ Branch))`。

#### 集合操作（要求**并相容 union-compatible**：属性数相同 + 对应属性同域）`[1.2 p37-45]`

**⑤ 并 ∪ (Union)** `R ∪ S`：R、S 或两者的全部元组，去重；最多 I+J 个元组。`[1.2 p37]`
**⑥ 差 − (Set difference)** `R − S`：在 R 但不在 S 的元组。`[1.2 p40]`
**⑦ 交 ∩ (Intersection)** `R ∩ S`：同时在 R 和 S 中的元组；可用基本操作表示 **`R ∩ S = R − (R − S)`**。`[1.2 p43]`

#### 关系代数典型例题（Hotel 数据库）★ `[1.2 p46-49]`
模式：`Hotel(hotelNo,hotelName,city)`、`Room(roomNo,hotelNo,type,price)`、`Booking(hotelNo,guestNo,dateFrom,dateTo,roomNo)`、`Guest(guestNo,guestName,guestAddress)`

| 题目 | 解答 |
|---|---|
| 1. 所有房间全部细节 | `Room` |
| 2. 北京的所有酒店 | `σ_city='Beijing'(Hotel)` |
| 3. 房价>£50 的酒店号 | `π_hotelNo(σ_price>50(Room))` |
| 4. Happy Hotel 所有房间的价格与类型 | `π_price,type(σ_hotelName='Happy'(Hotel ⋈ Room))` |
| 5. 所有酒店的所有房间 | `Hotel ⋈ Room` |
| 6. 有房价>£50 的酒店名 | `π_hotelName(σ_price>50(Hotel ⋈ Room))` |
| 7. 当前住在 Happy Hotel 的客人号 | `R1 = σ_hotelName='Happy' ∧ dateFrom≤current_Date() ∧ dateTo>current_Date()(Hotel ⋈ Booking…)`；结果 `π_guestNo(R1)` |
| 8. 曾订过北京酒店的客人号 | `π_guestNo(σ_city='Beijing'(Booking ⋈ Hotel))` |
| 9. 住过 Executive 房型的客人号与名 | `π_guestNo,guestName(σ_type='Executive'(Guest ⋈ Booking ⋈ Room))` |

> **解题技巧**：①先确定要哪些列（投影）和过滤条件（选择）；②跨多表时先用自然连接把相关表连起来；③涉及日期用 `current_Date()`；④"既…又…"用 ∩，"…但不…"用 −，"…或…"用 ∪。

## 1.3 实体-关系建模 (ER Modelling)

### A. 基本概念 `[1.3 p6-9]`
- ER 建模是**高层概念建模 (high-level conceptual modelling)** 技术；由 **Peter Chen (1976)** 提出。`[1.3 p6]`
- 三大构件 (building blocks)：实体 (Entity)、属性 (Attribute)、关系 (Relationship)。
- **实体 (Entity)**：要存储数据的"事物"，具有独立存在性的同类对象组；可物理存在（学生、课本）或概念存在（模块、考试）。用**矩形**表示，名称用**单数、大写**置于顶部。`[1.3 p7-8]`
- **属性 (Attribute)**：描述实体的离散数据元素，列于实体名下方；名称需自解释且唯一。**标识符/主键 (identifier / primary key)** 唯一标识实体实例（用星号 `*` 标注）。`[1.3 p9]`

### B. 二元关系的多重性 (Multiplicity) ★必考 `[1.3 p13-19, p31-33]`
- **多重性 (Multiplicity)**：与某实体单个实例相关联的另一实体可能出现的**数量（或范围）**；体现**业务规则 (business rules)**。`[1.3 p31]`
- 三种二元关系：

| 类型 | 记法 | 说明与例子 |
|---|---|---|
| 一对一 (1:1) | 1 — 1 | DEPT–EMP 的 boss 关系（一个部门一个老板）`[1.3 p27]` |
| 一对多 (1:m / 1:*) | 1 — * | 一个国家有多个城市，一个城市只属于一个国家 `[1.3 p14]` |
| 多对多 (m:m / *:*) | * — * | 一次销售含多件商品，一件商品出现在多次销售 `[1.3 p18]` |

- **m:m 的处理**：无法直接记录关系上的属性（如数量、总价）→ 创建第三个**关联实体 (associative entity)**，将 m:m 拆成**两个 1:m 关系**。`[1.3 p18-19]`
  - 例：`SALE —1:* LINEITEM *:1— ITEM`，LINEITEM 含 saleNo、itemNo、itemQuantity、totalPrice。

### C. 递归关系 (Recursive Relationship) `[1.3 p27-29]`
- **同一实体类型以不同角色 (role) 参与同一关系多次**。
- 例：员工的"老板"也是员工 → person-boss 为**递归 1:m 关系**。`[1.3 p28]`
- 可给关系标注**角色名 (role names)** 表明各参与方的作用。`[1.3 p29]`

### D. 关系的度 (Degree of Relationship) `[1.3 p34-41]`
- **度 = 参与关系的实体数量**：二元 (binary, 2)、三元 (ternary, 3)、四元 (quaternary, 4)、n 元 (n-ary)。
- **三元关系 (Ternary) ≠ 三个二元关系**（重要易错点！）。`[1.3 p35, p41]`
  - 例："Doctor prescribes patients medicines"、"Vendor supplies Parts to Warehouses"。
  - 某些属性（如 Unit Cost）**无法**归属于任何一个二元关系，只能依附三元关系（Supply Schedule）。`[1.3 p37]`
- **n 元关系中实体的多重性**：固定其余 (n−1) 个实体的值时，该实体可能出现的数量（范围）。`[1.3 p39]`
- True/False 练习结论：三元=三实体(T)；四实体=四元(T)；三元可拆成三个二元(**F**)。`[1.3 p41]`

### E. 数据建模质量 (Data Model Quality) `[1.3 p47-60]`
- 数据建模目标：识别**要存储的事实**；不关心如何存储、如何处理；是客户与设计者的**迭代式 (iterative)** 协作。`[1.3 p48]`
- 优质数据模型 = **结构良好 (well-formed)** + **高保真 (high-fidelity)**。`[1.3 p49]`
  - **Well-formed**：遵守构造规则、无歧义；所有实体/属性/关系/标识符都已定义；用正确记法表示并标注关系；属性名有意义且唯一。`[1.3 p51]`
  - **High-fidelity**：忠实反映现实；关系的度正确；模型完整、可理解、准确；对客户有意义。`[1.3 p52]`
- 建模提示 (Hints)：`[1.3 p56-58]`
  - 必要时发明标识符（键）；**键只用于标识**这一个目的。
  - 数据模型不隐含排序；若需排序则建一个属性。
  - 注意**同义词 (Synonyms)**（不同词同义）与**同形异义词 (Homonyms)**（同词异义）。
  - 关联实体若无现实名称，可拼接实体名命名。
  - 标注关系以避免歧义。
- **假设 (Assumptions)** ★：需求未明说但建模必需时**必须做假设**；不同假设导致不同模型；假设须合理；**做了假设必须明确写出**（考试/作业重要！）。`[1.3 p59-60, p63]`

## 1.4 逻辑数据库设计 (Logical Design — ER 映射到关系模型)

> 总目标：把概念 ER 模型转成一组关系（确定外键放哪里、是否新建关系）。`[1.4 p23]`

### A. 实体映射 (Entity) `[1.4 p4]`
- 每个实体 → 一个关系，包含其全部属性。
- **复合属性**只保留其组成的简单属性（拆成多列）。
- 例：`STAFF(staffNo, fName, lName, position, sex, DoB)`。

### B. 1:m (1:*) 二元关系 ★最常用 `[1.4 p5-6]`
- **规则**：把"一"端实体的主键作为**外键**复制到"多"端关系中。
- 例：`COUNTRY(countryCode, countryName, language)`、`CITY(cityCode, cityName, population, area, countryCode)`。
- 练习：`CLASS(classNo, name, year)`、`STUDENT(studentID, sName, gender, DoB, classNo)`。

### C. 1:1 二元关系（按参与性 participation 分情况）★ `[1.4 p7-11]`

| 情形 | 映射规则 |
|---|---|
| 双方都**强制参与** (mandatory both sides) | **合并为一个关系**；选其中一个主键作主键，另一个作候选键 |
| **仅一方强制参与** (mandatory one side) | 两个关系；把**可选参与方的主键**作为外键放入**强制参与方**关系 |
| 双方都**可选参与** (optional both sides) | **新建一个关系**表示该联系，含两个实体主键的副本（作外键，须重命名表明用途） |

- 一般经验：**选择能产生最少 null 的一方**放外键（对客户更清晰）。`[1.4 p9]`
- 练习 2（车位例，EMPLOYEE 可选参与）：`EMPLOYEE(empID, name, department)`、`CARPARKSPACE(spaceID, location, size, empID)`。`[1.4 p11]`

### D. 递归关系映射 `[1.4 p12-17]`
- **1:m 递归**：同 1:m 规则，在"多"端加外键列。例：`Emp(empno, empfname, empsalary, deptname, bossempno)`，bossempno 指向员工老板的 empno（或 null）。`[1.4 p13]`
- **1:1 递归**：
  - 双方强制 → 一个关系含两份主键副本，一份作外键并重命名。
  - 双方可选 → 新建关系，两份主键副本作外键并重命名。
  - 仅一方强制 → 可按"双强制"或"双可选"任一方式处理。`[1.4 p14]`
- 练习 4（婚姻，双方可选）：`PERSON(personID, name, DoB, gender)`、`MARRIAGE(person1ID, person2ID)`。`[1.4 p17]`

### E. m:m (*:*) 二元关系 ★ `[1.4 p18-20]`
- **规则**：新建一个关系表示联系；含指向两个参与实体的外键（这些外键**共同组成新关系的主键**）；再加关系自身的属性。
- 例：`SALE(saleNo,saleDate,saleText)`、`ITEM(ItemNo,itemName,itemType,itemColour)`、`LINEITEM(saleNo, ItemNo, itemQuantity, totalPrice)`。
- 例：`Viewing(clientNo, propertyNo, dateView, comment)`。`[1.4 p20]`

### F. 复杂关系 (Complex / n 元) `[1.4 p21]`
- 新建关系表示联系，含关系属性；把各参与实体主键作外键复制进来；表示"多"端 (1..\*, 0..\*) 的外键通常**组成新关系主键**（可能还需新属性参与主键）。

### G. 多值属性 (Multi-Valued Attributes) `[1.4 p22]`
- **规则**：新建关系，含实体主键（作外键）。
- 例：分行多个电话号 → `Telephone(telNo, BranchNo)`，使一个 Branch 可拥有多个电话号。

> **映射规则速查总结** `[1.4 p23]`：实体→表；1:m→外键放多端；1:1→看参与性（合并/外键/新关系）；m:m 与复杂关系→新建关系 + 外键组成主键；多值属性→新建关系。

## Tutorial 1 — 习题与答案

### 第 1 题：关系代数（航空数据库）`[Tut1 p2-6]`
模式：`Employee(empNo,eName,salary,position)`、`Aircraft(aircraftNo,aName,aModel,flyingRange)`、`Flight(flightNo,aircraftNo,from,to,flightDistance,departTime,arriveTime)`、`Certified(empNo,aircraftNo)`

| 小题 | 题意 | 答案 |
|---|---|---|

### 第 2 题：过去考题 — 牙科诊所 ER 模型 `[Tut1 p7-9]`
需求要点：牙医 (Dentist)、病人 (Patient)、治疗 (Treatment)；病人可与牙医预约接受治疗，记录预约日期/时间/时长，牙医可记录评论。

**实体与属性**：`[Tut1 p8]`
- `PATIENT(*p_id, p_name, DoB, address, …)`
- `DENTIST(*d_id, d_name, qualification)`
- `TREATMENT(*t_id, t_name, material, procedure)`

**关系**：三方预约 → 关联实体 **APPOINTMENT**，连接 Patient、Dentist、Treatment（各为 1:\* 关系）`[Tut1 p9]`
- `APPOINTMENT(*appid, p_id, d_id, t_id, date, time, Duration, comments)`
- 即：PATIENT 1—\* APPOINTMENT \*—1 TREATMENT，DENTIST 1—\* APPOINTMENT。

> **解题要点**：预约同时关联三个实体并带自身属性（date/time/duration/comments），用关联实体表示最清晰；记得**写明假设**（如一次预约对应一名病人、一名牙医、一种治疗）。
