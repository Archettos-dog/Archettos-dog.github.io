## 一、高级规范化(Advanced Normalization,3.1)

### 1. BCNF(Boyce–Codd Normal Form,Boyce–Codd 范式)

**定义(必背)**:一个关系属于 BCNF,当且仅当它的**每个决定因素(determinant)都是候选键(candidate key)** [3.1 p4]

**3NF 与 BCNF 的区别(高频考点)**:对于函数依赖 A → B [3.1 p5]
- **3NF** 允许:B 是候选键属性(candidate-key attribute)且 A 不是候选键
- **BCNF** 要求:A 必须是候选键
- 即 BCNF 比 3NF 更严格:每个 BCNF 关系都是 3NF,但 3NF 关系不一定是 BCNF [3.1 p13]

**2NF / 3NF 一般定义(以候选键表述)** [3.1 p10]:
- **2NF**:1NF + 每个非候选键属性对任何候选键都**完全函数依赖**(fully functionally dependent)
- **3NF**:1NF + 2NF + 没有非候选键属性**传递依赖**(transitively dependent)于任何候选键

**3NF 关系可能违反 BCNF 的情形(判断题常考)** [3.1 p13]:
- 关系含有**两个(或以上)复合候选键(composite candidate keys)**;且
- 候选键**重叠(overlap)**,即至少有一个公共属性
- 对 3NF 关系而言,违反 BCNF 的情况相当罕见

### 2. BCNF 判定典型例题

**DreamHome 基本关系均为 BCNF**(所有决定因素都是候选键)[3.1 p6]:如 `Rental(clientNo, propertyNo, rentStart, rentFinish)` 有三个决定因素,全部是候选键 → BCNF。

**ClientInterview 例子(必会)** [3.1 p7–12]:
- 背景:客户面试,员工当天被分配到固定房间;一个房间一天内可分配给多名员工;客户在某一天只面试一次 [3.1 p7]
- ClientInterview(clientNo, interviewDate, interviewTime, staffNo, roomNo) 的 FDs [3.1 p8]:
  - fd1: clientNo, interviewDate → interviewTime, staffNo, roomNo(主键)
  - fd2: staffNo, interviewDate, interviewTime → clientNo(候选键)
  - fd3: roomNo, interviewDate, interviewTime → staffNo, clientNo(候选键)
  - fd4: **staffNo, interviewDate → roomNo(决定因素不是候选键 → 违反 BCNF)**
- 候选键:(clientNo, interviewDate)、(staffNo, interviewDate, interviewTime)、(roomNo, interviewDate, interviewTime) [3.1 p9]
- 后果:更新异常(update anomaly)——改 SG5 在 13-May-05 的房间号要更新两个元组 [3.1 p11]
- **分解到 BCNF**(移除违反 BCNF 的 FD)[3.1 p12]:
  - Interview(clientNo, interviewDate, interviewTime, staffNo)
  - StaffRoom(staffNo, interviewDate, roomNo)

**练习 1**:Apply(studentNo, collegeName, cCity, date, major),fd1: collegeName → cCity;fd2: studentNo, collegeName → date, major。候选键是 (studentNo, collegeName),fd1 的决定因素不是候选键 → **不是 BCNF** [3.1 p14]

**练习 2/3**:Z(A,B,C,D,E),fd1: A,B → C,D,E;fd2: B,C → D。候选键 (A,B),fd2 违反 BCNF → 不是 BCNF;分解为 **Z1(B, C, D) 和 Z2(A, B, C, E)** [3.1 p15, p17]

### 3. BCNF 分解算法(必背)[3.1 p16]

对带 FDs 的关系 R:
1. 计算 R 的键
2. 重复直到所有关系都是 BCNF:
   - 任选一个含违反 BCNF 的依赖 A → B 的关系 R'
   - 把 R' 分解为 **R1(A, B)** 和 **R2(A, rest)**(rest = 其余属性,A 保留在两个关系中)
   - 重新计算 R1、R2 的 FDs 和键

### 4. BCNF 的局限(简答题素材)[3.1 p18–21]

- StudentLabTime(Student, courseLab, time) 例子:FDs 为 `Student, courseLab → time` 和 `time → courseLab`;候选键 (Student, courseLab) 和 (Student, time) [3.1 p18–19]
- 按算法分解后(Student, time)+(time, courseLab)**不可接受**:同一学生对同一 courseLab 可记录多个时间,**丢失了 FD:Student, courseLab → time** [3.1 p20]
- 结论(判断题常考):**形如 {AB → C, C → B} 的 FD 集合无法用 BCNF 模式表示**;可用 **EKNF(Elementary Key Normal Form,基本键范式)** 消除异常但不符合 BCNF [3.1 p21]

### 5. 多值依赖(MVD)与 4NF

- 动机:BCNF 消除了 FD 引起的异常,但**多值依赖(Multi-valued Dependency, MVD)**仍会导致数据冗余 [3.1 p23]
- **MVD 定义**:属性 A、B、C 之间,A 的每个值对应一组 B 值和一组 C 值,但 **B 的取值集合与 C 的取值集合相互独立**;记作 A −>> B,A −>> C [3.1 p25]
- **平凡(trivial)与非平凡(nontrivial)MVD** [3.1 p26]:
  - A −>> B 是平凡的,若 (a) B ⊆ A,或 (b) A ∪ B = R(全部属性)
  - 两者都不满足则是非平凡的;**只有非平凡 MVD 才构成约束**
- **4NF 定义(必背)**:一个关系属于 4NF,当且仅当对每个非平凡多值依赖 A −>> B,**A 是该关系的候选键** [3.1 p27]

**典型例子 BranchStaffOwner** [3.1 p24, p28]:branchNo 对应一组员工 sName 和一组业主 oName,员工与业主之间无关联 → 非平凡 MVD:branchNo −>> sName,branchNo −>> oName;branchNo 不是候选键 → 不在 4NF。**分解到 4NF**:BranchStaff(branchNo, sName) + BranchOwner(branchNo, oName)。

**练习 4**:Student(studentID, sport, subject),有非平凡 MVD:studentID −>> sport、studentID −>> subject;studentID 不是候选键 → **不在 4NF**(分解为 (studentID, sport) + (studentID, subject))[3.1 p29]

### 6. 分解性质(Decomposition Properties,高频判断题)[3.1 p30–31]

| 性质 | 含义 |
|---|---|
| 无损(lossless) | 拆分关系时数据不丢失、不凭空产生 |
| 保持依赖(dependency preservation) | 拆分后 FDs 仍被保留 |

- **规范化到 3NF:总是无损且保持依赖** [3.1 p31]
- **规范化到 BCNF:无损,但可能不保持所有依赖** [3.1 p31](例:StudentLabTime [3.1 p20])

### 7. 反规范化(Denormalization)[3.1 p32–33]

- 规范化的好处:消除数据冗余,解决 INSERT/UPDATE/DELETE 异常,便于维护一致性;代价:表更多,连接(join)开销大 [3.1 p32]
- **何时考虑反规范化**(三个条件)[3.1 p33]:
  1. 数据库速度无法接受(不只是有点慢)
  2. INSERT/UPDATE/DELETE 很少
  3. 大量涉及多表连接的 SELECT

## 二、事务管理(Transaction Management,3.2)

### 1. 事务与 ACID

**事务(Transaction)定义**:由用户或应用执行的、读取或更新数据库内容的一个动作或一系列动作;是数据库上的**逻辑工作单元(logical unit of work)**;把数据库从一个一致状态转换到另一个一致状态(执行过程中一致性可被暂时违反)[3.2 p4]

**ACID 四性质(必背)** [3.2 p5]:

| 性质 | 含义 |
|---|---|
| 原子性(Atomicity) | "全做或全不做"(all or nothing),事务中所有动作要么全部完成要么全不完成 |
| 一致性(Consistency) | 必须把数据库从一个有效状态变换到另一个有效状态 |
| 隔离性(Isolation) | 未完成事务的部分效果对其他事务不可见(事务相互独立执行) |
| 持久性(Durability) | 已提交事务的效果是永久的,不能因之后的故障而丢失 |

转账记忆例(A 转 £50 给 B)[3.2 p6]:原子性=不能只扣 A 不加 B;一致性=钱不会凭空增减;隔离性=完成前其他查询看不到 A、B 变化;持久性=钱不会退回 A。

**练习 1(判断,答案为推导,文中未给)** [3.2 p7]:正确的是 **B**(原子性=全做或全不做)和 **D**(持久性=提交后效果永久);A 错(C 是 Consistency 不是 Compatibility),C 错(隔离性是**不能**看到其他事务的部分修改)。

**事务两种结果(outcomes)** [3.2 p8]:
- **提交(commit)**:成功,达到新一致状态,修改保存并对其他事务可见
- **中止(abort)**:失败,必须恢复到事务开始前的一致状态,即**回滚(rollback / undo)**,如同事务从未存在过

### 2. 三大并发问题(必背,会画/读时刻表)

并发动机:大型数据库多人使用,若只能串行执行,长事务(如备份)会让其他事务长时间等待;并发通过**交错(interleave)**操作实现,但破坏隔离性会违反 ACID [3.2 p10–11]

**(1) 丢失更新问题(Lost Update Problem)** [3.2 p12–13]
- 一个用户已成功完成的更新被另一用户覆盖。T1 读 X 期间 X 被 T2 修改,导致某个事务的更新被丢弃
- 经典时刻表(X 初值 100,T1 取 £10、T2 存 £100,串行结果应为 190):

| Time | T1 | T2 | X |
|---|---|---|---|
| t1 | | begin_transaction | 100 |
| t2 | begin_transaction | read(X) | 100 |
| t3 | read(X) | X = X+100 | 100 |
| t4 | X = X−10 | write(X) | 200 |
| t5 | write(X) | commit | **90** |
| t6 | commit | | 90 |

- T2 的更新被覆盖,最终 X=90 而非 190。解决:阻止 T1 在 T2 更新完成前读 X [3.2 p12]

**(2) 未提交依赖问题(Uncommitted Dependency Problem,又称脏读 dirty read)** [3.2 p14–15]
- 一个事务看到了另一**未提交**事务的中间结果;后者回滚(rollback)时,前者并不知情
- 经典时刻表:T4 把 X 改为 200 后 rollback(X 应回到 100),但 T3 已读到 200 并据此减 10,得 190(正确应为 90)[3.2 p14]
- 解决:阻止 T3 在 T4 提交或中止之前读 X

**(3) 不一致分析问题(Inconsistent Analysis Problem)** [3.2 p16–17]
- 一个事务读多个值期间,另一事务更新了其中部分值
- 经典例子:T6 对 X(100)、Y(50)、Z(25) 求和,期间 T5 从 X 转 £10 到 Z;T6 读到旧 X(100)和新 Z(35),sum=185(偏高 10,正确为 175)[3.2 p16–17]
- 解决:阻止 T6 在 T5 完成更新前读 X 和 Z

**练习 2(答案在课件中)** [3.2 p18]:T1 更新 X 后 rollback,T2 在 rollback 前已读 X 并提交 → **未提交依赖问题**。

> **辨析技巧**:看时刻表先找 rollback——有 rollback 且别的事务读了其修改 → 未提交依赖;两个事务都写同一项且一个覆盖另一个 → 丢失更新;一个事务在求和/统计多个值 → 不一致分析。

### 3. 调度与可串行化(Serialisability)

- **并发控制(concurrency control)**:管理数据库上同时发生的操作、使其互不干扰的过程 [3.2 p20]
- **调度(schedule)**:一组并发事务的操作序列,保持每个事务内部操作的先后顺序 [3.2 p21]
- **串行调度(serial schedule)**:各事务的操作连续执行,无交错 [3.2 p21];串行调度保证无干扰、保持一致性,但**不同串行顺序的结果不保证相同** [3.2 p22]
- **非串行调度(nonserial schedule)**:来自多个并发事务的操作相互交错 [3.2 p25]
- **可串行化(serialisable)调度**:与**某个**串行调度等价的非串行调度;可串行化的目标是找到允许并发执行又互不干扰的非串行调度 [3.2 p24–25]

**读/写顺序何时重要(三规则)** [3.2 p26]:
1. 两个事务都**只读**同一数据项 → 不冲突,顺序无关
2. 读/写**完全不同**的数据项 → 不冲突,顺序无关
3. 一个事务**写**某数据项,另一个**读或写同一数据项** → 执行顺序重要

**冲突(conflict)与冲突可串行化** [3.2 p28]:
- 两事务冲突 ⟺ 使用**同一资源**且**至少有一个是写**;都只读 → 不冲突;不同资源 → 不冲突
- **冲突可串行化(conflict serialisable)**:调度中的事务存在冲突,但调度仍可串行化 [3.2 p28–29]

**练习 3(判断,答案为推导,文中未给)** [3.2 p30]:正确的是 **A**(非串行调度的最终结果可能与串行调度不同)和 **B**(若结果与任何串行调度都不同,则不可串行化);C 错(T1 读 A,B,C,T2 读 B,C,D 且只写 D——共同项 B、C 都是只读,无冲突);D 错(都读写 E,至少一个写且同一资源 → 有冲突)。

### 4. 锁(Locking)与两阶段锁(2PL)

**两类基本并发控制技术** [3.2 p32]:**锁(locking)**与**时间戳(timestamping)**——都是保守(conservative)方法,在可能冲突时延迟事务;**乐观(optimistic)方法**假设冲突罕见,仅在提交时检查冲突。

**两种锁** [3.2 p33]:
- **共享锁(shared lock,读锁 read-lock)**:多个事务可同时读同一资源,但此时任何事务都不能改它 [3.2 p34]
- **排他锁(exclusive lock,写锁 write-lock)**:一个事务独占写;其他事务此时不能读也不能写 [3.2 p34]
- 有些系统允许读锁**升级(upgrade)**为排他锁,或排他锁**降级(downgrade)**为共享锁 [3.2 p34]

**锁的基本规则(必背)** [3.2 p35]:
- 读之前必须获得读锁;写之前必须获得写锁
- 锁在 commit/rollback 时释放
- 不能在被其他事务**写锁定**的资源上获得任何锁
- 不能在被其他事务锁定(无论读/写锁)的资源上获得**写锁**
- 请求的锁不可用时,事务**等待(wait)**

**只有锁还不够(重要反例)** [3.2 p36–41]:T1(x=x+100, y=y−100)与 T2(x=x*1.1, y=y*1.1)都正确加锁但**用完即解锁**:
- 串行 T1→T2:X=220, Y=330;串行 T2→T1:X=210, Y=340 [3.2 p37–38]
- 交错执行得 X=220, Y=340,与任何串行结果都不同 → **不可串行化** [3.2 p39–40]
- 根源:**锁释放得太早**,失去隔离性与原子性;需要约束锁/解锁操作位置的额外协议 [3.2 p41]

**两阶段锁(Two-Phase Locking, 2PL)定义(必背)** [3.2 p43]:
- 事务中**所有加锁操作都先于第一个解锁操作**
- 原则:访问任何数据项前必须先加锁;**一旦释放过锁,就不能再加新锁**
- 两个阶段:

```
锁数量
  ▲      ___________
  |     /           \
  |    /             \
  |   /               \
  └──────────────────────► 时间
   增长阶段     收缩阶段
  (Growing:     (Shrinking:
   只加锁不放锁)  只放锁不加锁)
```
  1. **增长阶段(growing phase)**:获取所有需要的锁,不能释放任何锁
  2. **收缩阶段(shrinking phase)**:释放锁,不能再获取任何新锁

**2PL 防止三大并发问题** [3.2 p44–52]:核心思路都是——先 write_lock,对方请求锁时只能 WAIT,直到持锁方 commit/unlock。防止不一致分析的完整解法(文字版)见 [3.2 p52]:T5 先 write_lock(X),T6 请求 read_lock(X) 进入 WAIT,T5 完成 X、Z 的更新并 Commit/unlock 后,T6 才依次读 X、Y、Z,得到正确 sum=175。(2PL 防止丢失更新、脏读的对应图解在 [3.2 p46, p49],解法模式同 Tutorial 3 练习 2,见下文第三部分)

**练习 4(判断,答案为推导,文中未给)** [3.2 p53]:正确的是 **B**(释放锁的时机对可串行化调度很重要)和 **C**(2PL 可保证可串行化);A 错(读/写一执行完就放锁不能保证 ACID,见 p36–40 反例);D 错(2PL 中释放锁后不能再获取新锁);E 错(一个事务持有 A 的读锁时,另一事务申请 A 的写锁不会被批准,必须等待)。

### 5. 2PL 的遗留问题:级联回滚与死锁 [3.2 p56]

**级联回滚(Cascading Rollback)** [3.2 p57–59]:
- 所有事务都遵循 2PL 时调度一定可串行化,但**锁释放时机**仍可能出问题:T1 故障回滚,**依赖 T1 操作的其他事务也必须回滚**,形成级联效应——一个事务失败导致多个失败 [3.2 p57]
- 危害:可能撤销大量已完成的工作 [3.2 p59]
- **预防方法:把所有锁的释放推迟到事务结束(Rigorous 2PL,严格两阶段锁)** [3.2 p59]

**死锁(Deadlock)** [3.2 p61–65]:
- 定义:两个(或多个)事务**各自等待对方持有的锁**被释放 [3.2 p61]
- **打破死锁的唯一方法:中止(abort)一个或多个事务**;死锁对用户应透明,DBMS 应自动重启事务 [3.2 p63]
- 处理技术:
  - **超时(timeouts)** [3.2 p64]:请求锁只等待系统设定的时间,超时则 DBMS 假定其可能死锁(即使实际上没有),中止并自动重启该事务
  - **死锁预防(deadlock prevention)** [3.2 p65]:DBMS 预判事务是否会引起死锁,不允许死锁发生。**保守 2PL(Conservative 2PL):事务开始时锁住全部所需数据项**;缺点:难以预测需要哪些锁、锁利用率(lock utilisation)低(长期持锁却很少使用)

> **三种 2PL 变体对比(综合 [3.2 p43, p59, p65])**:基本 2PL=加锁全部先于解锁;Rigorous 2PL=持锁到事务结束(防级联回滚);Conservative 2PL=开始时锁全部数据项(防死锁)。

### 6. 数据粒度(Granularity)[3.2 p67–68]

- 并发控制协议保护单位的大小,从粗到细:**整个数据库 → 文件 → 页(page)→ 记录(record)→ 记录的字段值(field value)** [3.2 p67]
- **权衡(tradeoff)**:粒度越粗,并发度越低;粒度越细,需要存储的锁信息越多;最佳粒度取决于事务类型 [3.2 p68]

### 7. 数据库恢复(Database Recovery)

- 定义:故障发生时把数据库恢复到正确状态的过程 [3.2 p69]
- **故障类型**(可考多选)[3.2 p69]:系统崩溃(丢失主存)、电源故障、磁盘损坏(丢失部分二级存储)、应用软件错误、自然灾害、用户失误、蓄意破坏(sabotage)
- **事务是恢复的基本单位**;恢复管理器(recovery manager)负责原子性和持久性 [3.2 p70]
- **redo/undo 基本规则(必背)** [3.2 p70]:
  - 故障发生在 **commit 之后、缓冲区刷入二级存储之前** → 为保证**持久性**,必须 **redo(rollforward,重做)**该事务的更新
  - 故障时事务**尚未提交** → 为保证**原子性**,必须 **undo(rollback,撤销)**该事务的所有影响
- **DBMS 应提供的恢复设施(4 项)** [3.2 p71]:备份机制(backup)、日志设施(logging)、检查点设施(checkpoint)、恢复管理器(recovery manager)

**日志文件(Log File)** [3.2 p72–73]:
- 包含所有数据库更新信息:事务记录 + 检查点记录;也常用于审计(auditing)[3.2 p72]
- **事务记录的内容(可考简答)** [3.2 p73]:事务标识符、日志记录类型(事务开始/insert/update/delete/abort/commit)、受影响数据项的标识符、**前像(before-image)**、**后像(after-image)**、日志管理信息

**检查点(Checkpointing,必背)** [3.2 p75]:
- 检查点=数据库与日志文件之间的**同步点**,所有缓冲区被**强制写入(force-written)**二级存储
- 检查点记录包含**所有活动事务的标识符**
- **崩溃后恢复规则:redo 检查点之后提交的所有事务;undo 崩溃时仍活动的所有事务**

**检查点恢复经典例题** [3.2 p76](原图为图片,下为依据该页文字重构的示意图):

```
t0 ──────── tc(检查点) ──────── tf(崩溃)
T1 ────────────────────────────────►  (跨tc, 崩溃时未提交 → undo)
T2 ──────────────┤commit             (tc前已写入磁盘 → 不处理)
T3 ──────┤commit                     (tc前已写入磁盘 → 不处理)
T4 ────────────────────┤commit       (tc后提交 → redo)
T5 ──────────────────────┤commit     (tc后提交 → redo)
T6 ─────────────────────────────────► (崩溃时未提交 → undo)
```
- 检查点 tc 时 T2、T3 的修改已写入二级存储 → 无需处理;**redo T4、T5(tc 后提交);undo T1、T6(崩溃时仍活动)** [3.2 p76]

## 三、Tutorial 3 典型例题(带解答)

### 练习 1:判断范式并规范化到 BCNF [T3 p2–4]

表:Branch-Staff(branchNo, branchAddress, telNo, staffNo, sName),一个员工只在一个分支工作。

**(a) 现在是第几范式?** [T3 p3]
- FDs:fd1: branchNo → branchAddress, telNo;fd2: staffNo → sName, branchNo
- 候选键 = 主键 = **staffNo**
- fd1 是对主键的**传递依赖**(staffNo → branchNo → branchAddress, telNo),违反 3NF;无部分依赖 → **该关系在 2NF**

**(b) 规范化到 BCNF 的过程** [T3 p4](原解答先给出规范化到 3NF 的三步,再验证结果已是 BCNF):
1. 识别每个关系的函数依赖;2. 识别主键;3. 把部分/传递依赖的属性连同其决定因素的副本移到新关系
- 移除传递依赖 fd1:**Branch(branchNo, branchAddress, telNo) + Staff(staffNo, sName, branchNo)**
- 两个新关系中决定因素(branchNo、staffNo)都是键 → 均为 BCNF ✓

### 练习 2:识别并发问题 + 2PL 改写(必会题型)[T3 p5–7]

T1(X = X−50)与 T2(X = X+300)交错执行,T2 的更新被 T1 覆盖。

**(a)** 这是**丢失更新问题(lost update problem)**:T1 读 X 期间 X 被 T2 修改,一个事务的更新被丢弃 [T3 p6]

**(b) 2PL 改写(背这个模板)** [T3 p7]:

| Time | T1 | T2 |
|---|---|---|
| t1 | | begin_transaction |
| t2 | begin_transaction | **Write_lock(X)** |
| t3 | **Write_lock(X)** | read(X) |
| t4 | **WAIT** | X = X+300 |
| t5 | **WAIT** | write(X) |
| t6 | **WAIT** | **Commit/Unlock(X)** |
| t7 | read(X) | |
| t8 | X = X−50 | |
| t9 | write(X) | |
| t10 | **Commit/Unlock(X)** | |

要点:① 读写前先 Write_lock;② 对方持锁时只能 WAIT;③ 锁保持到 Commit 才释放(Commit/Unlock 写在一起)。

### 练习 3:判断题(答案为推导,文中未给)[T3 p8]

正确的是 **B、C、D**:
- A 错:开始时获取全部锁(保守 2PL)防的是**死锁**;级联回滚取决于**锁释放时机**(需持锁到事务结束,即 Rigorous 2PL)[3.2 p59, p65]
- B 对:开始时获取全部锁则不会"持有并等待" → 不会死锁 [3.2 p65]
- C 对:超时可以解决死锁 [3.2 p64]
- D 对:超时机制下 DBMS 可能中止一个并未死锁的事务 [3.2 p64]

### 练习 4:检查点恢复 [T3 p9–10]

t0 开始,tc 检查点,tf 断电。解答 [T3 p10]:
- tc 时 T1、T2 的修改已写入二级存储 → **T1、T2 无需处理**
- **redo T4、T5**(检查点后提交);**undo T3**(崩溃时未提交)
- (注意与课件 [3.2 p76] 例子事务编号不同,但规则完全一致:tc 前已提交不处理、tc 后提交 redo、崩溃时活动 undo)

## 四、本周高频考点速查 & 易错点

1. **BCNF 判据**:每个决定因素都是候选键;与 3NF 的差异表述 [3.1 p4–5]
2. **BCNF 分解模板**:违反的 A→B ⟹ R1(A,B) + R2(A,rest) [3.1 p16]
3. **{AB→C, C→B} 无法表示为 BCNF**(BCNF 分解可能丢失依赖) [3.1 p21]
4. **3NF 分解总是无损+保持依赖;BCNF 分解无损但可能不保持依赖** [3.1 p31]
5. **4NF 判据**:每个非平凡 MVD A−>>B 的 A 都是候选键 [3.1 p27]
6. **ACID 拼写陷阱**:C 是 Consistency(一致性),不是 Compatibility [3.2 p5, p7]
7. **三大并发问题的识别**:有 rollback + 他人读过其修改 → 脏读;互相覆盖 → 丢失更新;求和中途被改 → 不一致分析 [3.2 p12–18]
8. **冲突判定**:同一资源 + 至少一个写;都是读不冲突 [3.2 p28]
9. **2PL 核心**:所有加锁先于所有解锁;放锁后不能再加锁 [3.2 p43]
10. **2PL 改写题模板**:Write_lock → 对方 WAIT → Commit/Unlock(Tutorial 3 练习 2)[T3 p7]
11. **2PL ≠ 万能**:仍有级联回滚(解法:Rigorous 2PL,持锁到结束)和死锁(解法:超时、保守 2PL)[3.2 p56–65]
12. **检查点恢复三分法**:tc 前已提交并写盘 → 不处理;tc 后提交 → redo;崩溃时活动 → undo [3.2 p75–76, T3 p10]
13. **日志事务记录六要素**,尤其 before-image / after-image [3.2 p73]
14. **粒度权衡**:粗 → 并发低;细 → 锁信息多 [3.2 p68]
