## 一、SQL 基础（2.1 SQL.pdf）

### 1. SQL 简介
- SQL 是面向转换的语言（transform-oriented language），两大组成部分：**DDL**（数据定义语言, Data Definition Language）定义数据库结构，**DML**（数据操纵语言, Data Manipulation Language）检索和更新数据 [2.1 p3, p5]
- SQL 是**非过程化的（non-procedural）**：只说明要什么数据，不说明如何获取；本质上是自由格式（free-format）[2.1 p3]
- SQL 有 ISO 标准，是关系数据库的正式与事实标准语言 [2.1 p4]
- DDL 命令：CREATE / ALTER / DROP；DML 命令：SELECT / INSERT / UPDATE / DELETE [2.1 p5, p83]

### 2. SELECT 完整语法（必背）[2.1 p72]
```sql
SELECT [DISTINCT | ALL] {* | columnExpression [AS newName] [,...]}
FROM   TableName [alias] [, ...]
[WHERE    condition]
[GROUP BY columnList]
[HAVING   groupCondition]
[ORDER BY columnList]
```
**执行顺序**：FROM（多表先做笛卡尔积）→ WHERE（过滤行）→ GROUP BY（分组）→ HAVING（过滤组）→ SELECT（投影/DISTINCT去重）→ ORDER BY（最后排序）。（综合 p35 "WHERE 先于 GROUP BY 执行" 与 p51 连接计算五步推导得出 [2.1 p35, p51]）

### 3. 基本查询要点
| 关键点 | 说明 | 页码 |
|---|---|---|
| `SELECT *` | 所有列的缩写 | [2.1 p7] |
| `DISTINCT` | 消除结果中的重复行 | [2.1 p12] |
| 计算字段（calculated field） | 如 `salary/12 AS monthlySalary`，用 `AS` 命名新列 | [2.1 p13-14] |
| 复合条件 | `WHERE city='London' OR city='Glasgow'` | [2.1 p17] |
| `BETWEEN a AND b` | **包含两个端点** | [2.1 p18] |
| `LIKE` 模式匹配 | `%` = 零个或多个任意字符；`_` = 任意单个字符 | [2.1 p20] |
| NULL 判断 | 必须显式用 `IS NULL` / `IS NOT NULL`，不能用 `= NULL` | [2.1 p21-22] |
| `ORDER BY` | `DESC` 降序；多列排序时先按主排序键，再按次排序键，如 `ORDER BY type, rent DESC` | [2.1 p23-25] |

**典型例题**：列出工资低于15000的不重复工资并命名为 SalaryBand：`SELECT DISTINCT salary AS SalaryBand FROM Staff WHERE salary < 15000;` [2.1 p16]

### 4. 聚合函数（Aggregate Functions）[2.1 p28-29]
- ISO 标准定义 5 个：**COUNT、SUM、AVG、MIN、MAX**
- 重要性质（易考判断/简答）：
  - 每个函数作用于单列、返回单值
  - **SUM 和 AVG 只能用于数值字段**；COUNT、MIN、MAX 可用于数值和非数值字段
  - 除 `COUNT(*)` 外，所有聚合函数**先剔除 NULL** 再计算；`COUNT(*)` 统计所有行（含 NULL 和重复值）
  - 可在列名前加 DISTINCT 去重：DISTINCT 对 MIN/MAX **无影响**，对 SUM/AVG **可能有影响** [2.1 p29, p31]
- **易错点**：聚合函数不能直接出现在 WHERE 中。`WHERE salary > AVG(salary)` 非法，必须用子查询：`WHERE salary > (SELECT AVG(salary) FROM Staff)` [2.1 p56-57]

### 5. GROUP BY 与 HAVING
- GROUP BY 用于分组求小计；SELECT 列表中每项必须对每组是单值，只能包含：列名、聚合函数、常量、以上组合的表达式 [2.1 p34]
- **SELECT 列表中的列名必须出现在 GROUP BY 中**，除非该列只用在聚合函数里 [2.1 p35]
- WHERE 与 GROUP BY 同时使用时，**WHERE 先执行**（先过滤行，再对剩余行分组）[2.1 p35]
- ISO 标准在 GROUP BY 中把两个 NULL 视为相等 [2.1 p35]
- **HAVING vs WHERE（高频考点）**：WHERE 过滤**单行**，HAVING 过滤**组**；HAVING 中的列名必须出现在 GROUP BY 列表中或在聚合函数内 [2.1 p38]

**典型例题**：每个超过1名员工的分支机构的人数与工资总和 [2.1 p39]：
```sql
SELECT branchNo, COUNT(staffNo) AS myCount, SUM(salary) AS mySum
FROM Staff
GROUP BY branchNo
HAVING COUNT(staffNo) > 1
ORDER BY branchNo;
```
类似练习：按 type 分组，`HAVING COUNT(*) > 3` [2.1 p41]

### 6. 多表查询（隐式连接）
- 结果列来自多个表时必须连接：FROM 中列多个表（逗号分隔），WHERE 指定连接列；可用**表别名（alias）**限定有歧义的列名 [2.1 p42]
- 例：`FROM Client c, Viewing v WHERE c.clientNo = v.clientNo` [2.1 p43]
- 三表连接：`WHERE b.branchNo = s.branchNo AND s.staffNo = p.staffNo` [2.1 p47]
- 连接+分组：`GROUP BY s.branchNo, s.staffNo` 多列分组 [2.1 p49]
- **连接的计算过程（5步，可考简答）**[2.1 p51]：
  1. 对 FROM 中各表做笛卡尔积（Cartesian product）
  2. 用 WHERE 条件过滤每行
  3. 对剩余行按 SELECT 列表求值生成结果行
  4. 若有 DISTINCT，消除重复行
  5. 若有 ORDER BY，排序

### 7. 子查询（Subqueries）
- 子查询（subquery / nested query）可嵌在外层 SELECT 的 WHERE 和 HAVING 子句中；也可出现在 INSERT、UPDATE、DELETE 中 [2.1 p52]
- **子查询规则（易考）**[2.1 p59]：
  - 子查询中**不能用 ORDER BY**（只能用于最外层 SELECT）
  - 子查询 SELECT 列表必须是单列名或表达式（EXISTS 的子查询除外）
  - 子查询作为比较运算的操作数时，必须出现在**右侧**
- 单值子查询（=）[2.1 p53]；聚合子查询 [2.1 p56]；`IN` 多层嵌套 [2.1 p60]
- **ANY / SOME / ALL**（作用于产生单列数值的子查询）[2.1 p63]：
  - `> ALL`：大于子查询所有值才为真（即大于最大值）[2.1 p66]
  - `> ANY` / `> SOME`：大于子查询任一值即为真（即大于最小值）[2.1 p64-65]
  - **子查询为空时：ALL 返回 true，ANY 返回 false** [2.1 p63]
- **EXISTS / NOT EXISTS**（只能用于子查询）[2.1 p67-68]：
  - 子查询有行返回 true，否则 false；找到一行即终止子查询处理
  - 只检查存在性，子查询可含任意多列，习惯写 `(SELECT * ...)`
  - **易错点**：必须有关联条件（如 `s.branchNo = b.branchNo`），否则子查询恒真，外层会返回所有行 [2.1 p70]
- **典型例题**：列出从未被任何客户看过的房产 [2.1 p71]：
```sql
SELECT p.propertyNo FROM PropertyForRent p
WHERE NOT EXISTS (SELECT * FROM Viewing v
                  WHERE v.propertyNo = p.propertyNo);
-- 等价写法：WHERE propertyNo NOT IN (SELECT propertyNo FROM Viewing)
```
- **子查询与连接可互换（会双向改写）**：Eg.24 的两层 IN 嵌套子查询（列出 '163 Main St' 分支员工管理的房产）可改写为三表连接 [2.1 p60, p62]：
```sql
-- 子查询写法 [2.1 p60]
SELECT propertyNo, street, city, postcode, type, rooms, rent
FROM PropertyForRent
WHERE staffNo IN (SELECT staffNo FROM Staff
                  WHERE branchNo = (SELECT branchNo FROM Branch
                                    WHERE street = '163 Main St'));
-- 等价的三表连接写法 [2.1 p62]
SELECT p.*
FROM Branch b, Staff s, PropertyForRent p
WHERE b.branchNo = s.branchNo
  AND s.staffNo = p.staffNo
  AND b.street = '163 Main St';
```

### 8. 数据更新语句
**UPDATE** [2.1 p73-76]
```sql
UPDATE TableName
SET col1 = value1 [, col2 = value2 ...]
[WHERE searchCondition]
```
- WHERE 可选：**省略则更新表中所有行**；例：全员加薪3% `SET salary = salary*1.03`；多列同时更新用逗号分隔 [2.1 p75-76]

**DELETE** [2.1 p77-78]
```sql
DELETE FROM TableName [WHERE searchCondition]
```
- 省略 WHERE 则删除**所有行**，但**不删除表本身** [2.1 p77]

**INSERT** [2.1 p79-82]
```sql
INSERT INTO TableName [(columnList)] VALUES (dataValueList)
```
- columnList 可省略：默认按 CREATE TABLE 时的列顺序列出全部列 [2.1 p79]
- 被省略的列必须建表时声明为允许 NULL 或有 DEFAULT [2.1 p79]
- dataValueList 与 columnList：数量一致、位置一一对应、类型兼容 [2.1 p80]
- MySQL 的 DATE 类型格式为 `'YYYY-MM-DD'`，范围 1000-01-01 至 9999-12-31 [2.1 p81]

### 9. DDL
- `CREATE TABLE 表名 (列名 数据类型 [DEFAULT 默认值] [列约束], ... | 表约束)` [2.1 p84-85]；属性按创建顺序排列，行无顺序 [2.1 p84]
- `DROP TABLE [IF EXISTS] 表名 [RESTRICT | CASCADE]` [2.1 p86]

## 二、SQL JOIN（2.2 SQLJOIN.pdf）

### 1. 各种 JOIN 一览（核心考点）[2.2 p18]
| JOIN 类型 | 行为 | 页码 |
|---|---|---|
| 隐式连接 `FROM A, B WHERE ...` | 相当于关系代数的 **theta 连接（theta join, ⋈T）**，WHERE 是谓词 | [2.2 p3] |
| `A NATURAL JOIN B` | 在**所有同名属性**上连接，结果**无重复属性** | [2.2 p4, p8, p18] |
| `A JOIN B USING (c)` | 只在指定属性 c 上连接，结果中 c 不重复；可以是列表 `USING (c1, c2)` | [2.2 p9, p18] |
| `A JOIN B ON A.x = B.x` | **不合并列**（两表的 x 都保留）；与 `FROM A, B WHERE A.x = B.x` 完全等价 | [2.2 p10, p18] |
| `A CROSS JOIN B` | 笛卡尔积（Cartesian product） | [2.2 p12-13] |
| `A LEFT JOIN B ON ...` | 外连接：左表行无匹配时补 NULL（保留左表所有行） | [2.2 p12, p14] |
| `A RIGHT JOIN B ON ...` | 右表行无匹配时补 NULL（保留右表所有行） | [2.2 p12, p15] |
| `A FULL JOIN B ON ...` | 任一表无匹配都补 NULL（两边都保留） | [2.2 p12, p16] |

- 以上 NATURAL JOIN / USING / ON 都属于**内连接（INNER JOIN）**：只输出匹配的行 [2.2 p12]

### 2. 易错点
- **NATURAL JOIN 陷阱**：当两表有多个同名列（如 Cid 和 City）时，会同时在所有同名列上匹配，结果可能不是想要的 [2.2 p7]。此时改用 `JOIN ... USING (Cid)` 只按指定列连接 [2.2 p9]
- LEFT JOIN 与 RIGHT JOIN 可互换：`A LEFT JOIN B` ≡ `B RIGHT JOIN A` [2.2 p17]

### 3. 典型例题
- "列出所有客户及其看房记录，**包括没有看过房的客户**" → 用 LEFT JOIN（无匹配补 NULL）[2.2 p17]：
```sql
SELECT c.clientNo, fName, lName, propertyNo, comment
FROM Client c LEFT JOIN Viewing v ON c.clientNo = v.clientNo;
```
- 同一查询的三种 JOIN 写法（NATURAL JOIN / USING / ON）要会互相转换 [2.2 p6, p11；Tutorial2 p8]

## 三、数据库设计方法论（2.3 Database Design Methodology.pdf）

### 1. 总体框架
- **设计方法论（design methodology）**：使用规程（procedures）、技术（techniques）、工具（tools）和文档辅助（documentation aids）来支持设计过程的结构化方法；由阶段（phases）组成，每个阶段含若干步骤（steps）[2.3 p3]
- **四个主要阶段** [2.3 p4]：
  1. 收集需求（Gather requirements）
  2. 概念数据库设计（Conceptual database design）
  3. 逻辑数据库设计（Logical database design）
  4. 物理数据库设计（Physical database design）
- 与 ANSI-SPARC 三级架构（External / Conceptual / Internal level）对应 [2.3 p5]

### 2. 三种设计的定义（必背简答题）[2.3 p6]
| 阶段 | 定义 | 关键词 |
|---|---|---|
| 概念设计（Conceptual） | 构建企业所用数据的模型，**独立于一切物理考虑** | 与 DBMS、物理实现无关 |
| 逻辑设计（Logical） | 把概念模型映射到逻辑模型（如关系模型），**独立于特定 DBMS** 和其他物理考虑 | 与具体 DBMS 无关 |
| 物理设计（Physical） | 给出数据库实现的描述（**面向特定 DBMS**）：基本关系、文件组织、索引设计、完整性约束、安全措施 | 依赖具体 DBMS |

### 3. 概念设计步骤（Step 1）[2.3 p7-8]
1.1 识别实体类型 → 1.2 识别关系类型 → 1.3 识别属性并关联到实体/关系 → 1.4 确定属性域 → 1.5 确定候选键/主键/备用键 → 1.6 考虑增强建模概念（可选）→ 1.7 检查模型冗余 → 1.8 用用户事务验证模型 → 1.9 与用户复审

- **Step 1.5 选主键的准则** [2.3 p9]：属性集合最小；值最不易改变；字符最少（文本型）；最大值最小（数值型）；用户角度最易用
- **Step 1.7 检查冗余** [2.3 p10]：重新审查 1:1 关系（可能是同一实体，如 Client 与 Renter）；移除冗余关系；考虑时间维度

### 4. 逻辑设计步骤（Step 2）[2.3 p13]
2.1 导出关系 → 2.2 **用规范化验证关系** → 2.3 用用户事务验证 → 2.4 检查完整性约束 → 2.5 与用户复审 → 2.6 合并为全局模型（可选）→ 2.7 检查未来扩展

- **Step 2.4 完整性约束类型** [2.3 p14]：必需数据（required data，不允许 NULL）；属性域约束；多重性（multiplicity）；**实体完整性（entity integrity，主键不能为 NULL）**；**参照完整性（referential integrity，外键）**；一般约束
- **参照完整性 6 种情况**（父表 Staff，子表 PropertyForRent）[2.3 p15]：向子表插入/删除子表行/更新子表外键/向父表插入/删除父表行/更新父表主键——其中删除父表行时可选策略：**NO ACTION、CASCADE、SET NULL、SET DEFAULT**
- 书写示例 [2.3 p16]：
```
Foreign Key staffNo references Staff(staffNo)
  ON UPDATE CASCADE ON DELETE SET NULL
```

### 5. 物理设计步骤（Step 3-8）[2.3 p17-18]
- Step 3 为目标 DBMS 翻译逻辑模型（设计基本关系、派生数据表示、一般约束）
- Step 4 设计文件组织和索引（分析事务、选文件组织、选索引、估计磁盘空间）
- Step 5 设计用户视图；Step 6 设计安全机制；Step 7 考虑引入受控冗余；Step 8 监控和调优运行系统

## 四、规范化（2.4 Normalization.pdf）

### 1. 目的与动机
- **规范化（Normalization）**：产生一组适合企业数据需求的关系的技术 [2.4 p4]
- "合适的关系集合"的特征 [2.4 p5]：支持数据需求的**最少属性**；逻辑上紧密相关的属性在同一关系中；**最小冗余**（每个属性只出现一次，**外键属性例外**）
- 好处：用户更易访问和维护数据；占用最小存储空间 [2.4 p6]

### 2. 数据冗余与更新异常（update anomalies）[2.4 p10]
含冗余信息的关系可能存在三类更新异常（以 StaffBranch 表为例，分支信息随每个员工重复存储）：
- **插入异常（insertion anomalies）**：插入新分支但暂无员工时无法插入（主键含 staffNo 不能为空）
- **删除异常（deletion anomalies）**：删除某分支最后一名员工时，该分支的信息也随之丢失
- **修改异常（modification anomalies）**：修改某分支地址必须更新所有该分支员工的行，易遗漏导致不一致

### 3. 分解（Decomposition）的两个重要性质 [2.4 p11]
- **无损连接性（lossless-join property）**：能从分解后的小关系还原出原关系的任何实例
- **依赖保持性（dependency preservation property）**：原关系上的约束可通过在各小关系上强制约束来维持

规范化的两种用法 [2.4 p12]：① 自底向上（bottom-up）直接创建关系集合；② 作为**验证技术**检查（如 ER 导出的）关系结构。

### 4. 函数依赖（Functional Dependency, FD）——核心概念
- **定义**：A、B 是关系 R 的属性，若 R 中 A 的每个值都恰好对应 B 的一个值，则 B 函数依赖于 A，记作 **A → B** [2.4 p13]
- FD 是属性**语义/含义**的性质，不能只凭一时的样本数据断定，必须**对所有时间都成立**（如 staffNo → sName 恒成立，但 sName → staffNo 不一定，因为可能重名）[2.4 p15-16]
- **决定因素（determinant）**：FD 箭头左侧的属性（组）[2.4 p15]
- FD 的三个主要特征 [2.4 p20]：决定因素与右侧属性是 1:1 关系；对所有时间成立；决定因素含维持依赖所需的**最少属性**
- **完全函数依赖（full functional dependency）**：B 函数依赖于 A，且不依赖于 A 的任何真子集 [2.4 p17]
- **部分依赖（partial dependency）**：A → B 中可从 A 去掉某属性而依赖仍成立（如 staffNo, sName → branchNo 中 sName 多余）[2.4 p19]
- **传递依赖（transitive dependency）**：若 A → B 且 B → C（且 A 不函数依赖于 B 或 C），则 C 通过 B 传递依赖于 A [2.4 p21]
  - 例：staffNo → branchNo，branchNo → bAddress，则 bAddress 通过 branchNo 传递依赖于 staffNo [2.4 p22]

### 5. 识别 FD 与候选键（解题技巧）
- 识别 FD：分析属性语义与属性间关系；通常由企业/客户提供（需求文档），缺失时设计者用常识与经验 [2.4 p24]
- 也可用样本数据识别 FD（假设样本能代表所有可能取值）[2.4 p27-29]
- **用 FD 找候选键** [2.4 p31]：识别 FD 的主要目的是找候选键。候选键 = 能唯一标识每个元组的属性（组）；不属于候选键的所有属性都应函数依赖于键；多个候选键中选一个作主键
- 例：StaffBranch 五个 FD 的决定因素中，**只有 staffNo 能决定全部其他属性** → 唯一候选键即主键 [2.4 p32]
- 例：Sample 关系中 (A,B) 和 (B,C) 都能决定全部属性 → 两个候选键 [2.4 p33]
- 练习：studentID → projectID, sName, pName；projectID → pName → 主键 studentID [2.4 p30, p34]

### 6. 规范化过程：UNF → 1NF → 2NF → 3NF（重中之重）

```
数据源 --转成表格--> UNF --去除重复组--> 1NF --去除对主键的部分依赖--> 2NF --去除对主键的传递依赖--> 3NF
```
[2.4 p50]

| 范式 | 定义 | 消除目标 | 页码 |
|---|---|---|---|
| UNF（未规范化形式, Unnormalized Form） | 含一个或多个**重复组（repeating groups）**的表 | — | [2.4 p36] |
| 1NF（第一范式, First Normal Form） | 每个行列交叉点**有且仅有一个值** | 重复组 | [2.4 p38] |
| 2NF（第二范式, Second Normal Form） | 1NF + 每个非主键属性**完全函数依赖**于主键 | 部分依赖 | [2.4 p41] |
| 3NF（第三范式, Third Normal Form） | 1NF + 2NF + 没有非主键属性**传递依赖**于主键 | 传递依赖 | [2.4 p45] |

- UNF→1NF 两种方法 [2.4 p38-39]：选定键属性，识别重复组，然后 ① 把数据填入空列"压平"（flattening），或 ② 把重复数据连同原键的副本放入单独的关系
- **1NF→2NF 三步法** [2.4 p42]：① 识别关系中的 FD；② 识别 1NF 关系的主键；③ 若存在对主键的部分依赖，把部分依赖的属性连同其**决定因素的副本**移入新关系
- **2NF→3NF 三步法** [2.4 p46]：① 识别 FD；② 识别主键；③ 若存在对主键的传递依赖，把传递依赖的属性连同其决定因素的副本移入新关系
- **一般定义（generic definitions）**：2NF/3NF 的严格定义是针对**任意候选键（candidate key）**而非仅主键 [2.4 p51]

### 7. 贯穿例子：ClientRental 的 1NF→3NF 分解 [2.4 p37-48]
1NF 关系 ClientRental(clientNo, propertyNo, cName, pAddress, rentStart, rentFinish, rent, ownerNo, oName)，FD 如下 [2.4 p43]：
```
fd1  clientNo, propertyNo → rentStart, rentFinish   （主键）
fd2  clientNo → cName                                （部分依赖）
fd3  propertyNo → pAddress, rent, ownerNo, oName     （部分依赖）
fd4  ownerNo → oName                                 （传递依赖）
fd5  clientNo, rentStart → propertyNo, ...           （候选键）
fd6  propertyNo, rentStart → clientNo, ...           （候选键）
```
- 去除部分依赖 fd2、fd3 得 **2NF** [2.4 p44]：`Client(clientNo, cName)`、`PropertyOwner(propertyNo, pAddress, rent, ownerNo, oName)`、`Rental(clientNo, propertyNo, rentStart, rentFinish)`
- PropertyOwner 中 propertyNo → ownerNo → oName 是传递依赖，去除得 **3NF** [2.4 p47-48]：
  `Client(clientNo, cName)`、`Rental(clientNo, propertyNo, rentStart, rentFinish)`、`PropertyForRent(propertyNo, pAddress, rent, ownerNo)`、`Owner(ownerNo, oName)`

### 8. 典型考题模板（Exercise 4）[2.4 p52-54]
题型："表 X 是否属于 2NF？说明理由，并演示规范化到 3NF 的过程。"
**答题套路**：
1. 列出所有 FD（如 fd1: staffNo → name；fd2: branchNo → branchCity；fd3: staffNo, branchNo → position, hoursPerWeek）
2. 确定主键（staffNo, branchNo）
3. 判断：fd1、fd2 是对主键的**部分依赖** → 不是 2NF
4. 去除部分依赖，分解为：`Staff(staffNo, name)`、`Branch(branchNo, branchCity)`、`Work(staffNo, branchNo, position, hoursPerWeek)`
5. 检查无传递依赖 → 已是 3NF

### 9. 易错点
- 判断 FD 方向：每个 A 值只对应一个 B 值时是 **A → B**（不是 B → A）[2.4 p13, p23]
- 主键属性**可以**函数决定关系中其余属性（这正是候选键的性质）[2.4 p23, p31]
- 找候选键时不要漏组合键：单个属性都不行时考虑属性组合 [2.4 p33]
