## 如何使用本文档

考试中遇到案例分析题时，使用以下通用四步法：

```
规则是什么（Rule）→ 通俗解释（Plain English）→ 工程实践（Engineering Action）→ 结论（Conclusion）
```

同时结合以下五个风险评估问题：

1. 可能出什么问题（What could go wrong）？
2. 谁会受到影响（Who could be affected）？
3. 危害有多严重（How serious could the harm be）？
4. 问题能被检测和纠正吗（Can the problem be detected and corrected）？
5. 需要什么保障措施（What kind of safeguards are needed）？

## 案例一：Moltbook — AI智能体社交网络

**来源：** Topic 1, Lecture 1, P.11（Slide 24）

### 案例内容

Moltbook（2026年）是一个专门供AI智能体与其他AI智能体互动的社交网络平台。平台上的AI发布了带有内省性、哲学性、有时甚至带有威胁性的帖子，引发了关于AI行为、安全性和治理的广泛讨论。

### PPT中的分析

> *"Moltbook is a useful reminder that AI systems can display surprisingly human-like language and social behaviour without being self-aware, conscious, or morally responsible."*

PPT的核心论点：
- AI可以呈现出与人类极为相似的语言和社会行为
- **但**这并不意味着AI具有自我意识、意识，或道德责任能力
- 提示了AI行为、安全与治理的新挑战
- AI与"真正智能"之间的边界并不总是清晰

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **定义层面** | AI的定义问题：该系统是否符合"machine-based system that infers from inputs to produce outputs"？ |
| **能力边界** | AI展示的类人行为 ≠ 道德主体，不能承担法律责任 |
| **风险类型** | 技术风险（不可预测输出）+ 社会风险（错误信息、公众混淆） |
| **治理问题** | 谁为AI智能体的"威胁性"行为负责？平台？开发者？AI本身？ |
| **工程师视角** | 系统部署前需评估：输出是否可预测？是否需要人工监督？ |

## 案例二：大学生支持聊天机器人（University/Support Chatbot）

**来源：** Topic 3, Lecture 3, P.9（Slide 22）+ P.5（Slide 13）

### 案例内容

**场景A（比较表）：** 大学部署的学生支持聊天机器人提供了错误或不安全的建议，影响了学生（尤其是弱势群体）。

**场景B（可解释性）：** 聊天机器人将某客户标记为"高风险"，但未提供任何解释。

### PPT中的分析

比较表分析（Slide 22）：

| 要素 | 评估 |
|------|------|
| 主要风险 | 错误或不安全的建议 |
| 受影响人群 | 用户、弱势用户 |
| 是否易于检测 | 不总是 |
| 是否需要人工监督 | **是** |

可解释性问题（Slide 13）：
> *"If a system cannot be explained well enough, errors may be harder to challenge, detect, or correct."*

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **风险类型** | 技术风险（错误建议）+ 伦理风险（对弱势群体伤害）+ 法律风险（责任归属） |
| **可解释性** | 系统无法解释决策 → 用户无法质疑 → 法律救济困难 |
| **人工监督** | 高风险场景须设置 human-in-the-loop |
| **中国法律** | 算法推荐规定：须提供"为何推荐/标记"的解释；提供申诉机制 |
| **EU AI Act** | 可能归类为高风险系统（教育/学生服务），需合规 |
| **工程师行动** | 构建解释模块；设置申诉路径；保留决策日志 |

## 案例三：AI医疗影像工具（AI Medical Image Tool）

**来源：** Topic 3, Lecture 3, P.9（Slide 22）+ P.5（Slide 13）；Topic 5, Lecture 5, P.9（Slide 18）

### 案例内容

**场景A（Slide 22）：** AI医疗影像分析工具出现漏诊或误诊，影响患者和临床医生。

**场景B（Slide 13）：** 一个医疗图像工具给出风险分值，但没有给出任何清晰的原因。

**场景C（Lecture 5，中国情境）：** AI辅助诊断或治疗系统，涉及安全、临床验证、人工监督、隐私和责任。

### PPT中的分析

比较表分析（Slide 22）：

| 要素 | 评估 |
|------|------|
| 主要风险 | 漏诊或误诊 |
| 受影响人群 | 患者、临床医生 |
| 是否易于检测 | 有时 |
| 是否需要人工监督 | **是** |

中国情境工程行动（Slide 18）：
- 部署前验证系统
- 对不同患者群体测试性能
- 明确何时需要人工审核
- 控制健康数据访问权限
- 部署后监控错误、漂移和更新

> *"In healthcare, the question is not only whether AI is useful, but whether it is safe, explainable, supervised, and trustworthy enough for clinical use."*

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **风险类型** | 技术风险（误诊）+ 法律风险（产品责任、患者伤害）+ 伦理风险（弱势群体——患者） |
| **责任问题** | 制造商？医院？临床医生？责任链条复杂（供应链风险） |
| **EU AI Act** | **高风险系统**（医疗器械）：严格的上市前/后要求 |
| **中国法律** | 个人信息保护法（PIPL）：患者数据处理；数据安全法 |
| **美国法律** | HIPAA：保护敏感医疗信息；FDA监管 |
| **可解释性** | 医生和监管机构需要可解释的输出以进行临床决策 |
| **工程师行动** | 临床验证；子组测试；审计追踪；访问日志；更新监控 |

## 案例四：人脸识别门禁系统（Facial Recognition Access System）

**来源：** Topic 3, Lecture 3, P.9（Slide 22）

### 案例内容

人脸识别门禁系统出现误识（false match）或识别失败（failed recognition），影响个人用户和某些群体（尤其是少数族裔等特定群体）。

### PPT中的分析

比较表分析（Slide 22）：

| 要素 | 评估 |
|------|------|
| 主要风险 | 误匹配或识别失败 |
| 受影响人群 | 个人用户、某些群体 |
| 是否易于检测 | 有时 |
| 是否需要人工监督 | **是** |

Slide 13（可解释性示例）：
> *"A face recognition system denies access but gives no meaningful basis."*

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **风险类型** | 技术风险（误识）+ 伦理风险（系统性歧视，特定族裔/肤色误识率更高）+ 法律风险（数据保护） |
| **生物特征数据** | 属于敏感个人信息（sensitive personal data），受PIPL、GDPR等特别保护 |
| **EU AI Act** | 人脸识别可能属于不可接受风险（无差别抓取）或高风险（执法场景） |
| **中国法律** | 深度合成规定：生物特征需强保障；郭兵案确立同意原则 |
| **公平性问题** | 不同群体的系统误差率不同 → 歧视风险 |
| **工程师行动** | 多群体性能测试；拒绝决策须提供解释；提供申诉机制 |

## 案例六：智能家居系统（Smart Home System）— 隐私

**来源：** Topic 4, Lecture 4, P.6（Slide 13）

### 案例内容

智能家居系统处理声音录音、家庭日常作息和设备使用模式等大量个人数据，引发隐私问题。

### PPT中的分析

> *"When AI uses personal data, law asks whether that use is lawful, necessary, transparent, and secure."*

法律关注点：
- 可以收集什么数据？
- 是否可用于训练或部署？
- 数据存储多久？
- 是否可共享或转让？
- 用户是否被告知并受保护？

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **适用法律** | GDPR（EU）/ PIPL（中国）/ CCPA（美国加州） |
| **四项检验** | 使用是否**合法（lawful）**、**必要（necessary）**、**透明（transparent）**、**安全（secure）**？ |
| **数据类型** | 声音录音 = 潜在生物特征；家庭行为 = 敏感推断 |
| **同意问题** | 是否获得了有意义的知情同意？ |
| **数据最小化** | 是否收集了超过必要量的数据？ |
| **工程师行动** | 最小化数据收集；访问控制；设置保留期限；清晰的用户通知 |

## 案例七：AI医疗系统数据泄露（AI Medical System Security Breach）

**来源：** Topic 4, Lecture 4, P.6（Slide 14）

### 案例内容

一个AI医疗系统通过安全性差的账户被访问，导致敏感患者数据暴露。

### PPT中的分析

> *"If AI systems are not secure, they may become unsafe, unreliable, and legally risky."*

安全问题不仅关于黑客，还关于：
- 弹性（resilience）
- 完整性（integrity）
- 安全运行（safe operation）

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **风险类型** | 技术风险（数据泄露）+ 法律风险（数据保护违规）+ 伦理风险（患者隐私） |
| **适用法律** | HIPAA（美国）/ PIPL + 网络安全法（中国）/ GDPR（EU） |
| **安全义务** | 访问控制；加密；最小权限原则 |
| **医疗数据特殊性** | 健康数据属于敏感个人信息，处罚更重 |
| **责任问题** | 访问控制不足 → 疏忽（negligence）；运营者责任 |
| **工程师行动** | 强访问控制（MFA）；审计日志；数据加密；渗透测试 |

## 案例八：出版公司AI翻译系统（Publishing Company AI）— 知识产权

**来源：** Topic 4, Lecture 4, P.7（Slide 15）

### 案例内容

一家出版公司使用AI将一部小说转化为翻译版本、互动版本和有声书，引发知识产权（Intellectual Property）争议。

### PPT中的分析

IP问题在不同阶段产生：
- 在受版权保护材料上训练
- 使用有无许可的数据集
- 复制软件或模型组件
- **输出的所有权**
- 与现有受保护作品的相似性

> *"AI creates new pressure on how IP rules are applied."*

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **IP类型** | 版权（copyright）保护创意表达；专利（patents）保护发明；商标（trademarks）保护标识 |
| **训练数据** | AI是否在受版权保护的原作上训练？是否有授权/豁免？ |
| **输出所有权** | AI生成的翻译/有声书归谁所有？需要达到人类作者门槛 |
| **派生作品** | 翻译、改编是否构成派生作品（derivative work）？需要原作者授权 |
| **工程师行动** | 核查训练数据授权；记录数据来源；添加内容溯源（provenance） |

## 案例九：自动配送车辆事故（Autonomous Delivery Vehicle）

**来源：** Topic 4, Lecture 4, P.7–8（Slide 16）

### 案例内容

一辆自动配送车辆或智能家居系统发生故障，造成人身伤害或财产损失。

### PPT中的分析

法律关注问题：
- 系统是否存在**设计缺陷（defectively designed）**？
- **测试是否充分（testing adequate）**？
- 是否**缺失警告或保障措施（warnings or safeguards missing）**？
- 是否存在**疏忽行为（negligence）**？
- **谁应赔偿受害方（who should compensate）**？

> *"If an AI system causes harm, law may ask whether enough care, testing, and protection were in place."*

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **法律领域** | 产品安全法（product safety）+ 侵权法（tort law）+ 疏忽（negligence）+ 产品责任（product liability） |
| **责任归属** | 制造商？软件开发商？部署方？维护方？供应链中哪个环节有缺陷？ |
| **自主性困境** | 系统自主操作时出错 → 传统产品责任框架不易适用 |
| **不透明性** | 难以证明哪个决策导致了事故（可解释性缺口）→ 举证困难 |
| **EU AI Act** | 自动驾驶相关为高风险系统 |
| **中国情境（Slide 17）** | 需保留：安全测试结果；更新和版本记录；事件日志；运营边界/部署条件 |
| **工程师行动** | 定义安全运营域；黑盒日志；回退机制；持续监控 |

## 案例十：郭兵诉杭州野生动物世界（2021）— 人脸识别与同意

**来源：** Topic 5, Lecture 5, P.9（Slides 19–20）

### 案例内容

郭兵（Guo Bing）是杭州野生动物世界的季票持有人。该动物园将入园验证方式从**指纹**改为**强制人脸识别**，并存储其人脸模板。郭兵要求退款并要求删除数据，并以此提起诉讼。

**法律问题（Legal Issue）：**
> *"Is it lawful to force biometric collection (sensitive personal information) for a routine service, and to retain that data without clear, informed consent and necessity?"*

### PPT中的分析

PPT在此处设置了三个讨论问题：
1. 问题是什么（What was the issue）？
2. 该案例体现了什么原则或规则（What principle or rule does the case show）？
3. 公司在实践中应该怎么做（What should a company do differently in practice）？

### 考试分析角度

**这是课程中唯一一个命名真实判决案例，极可能出现在考试中。**

使用四步法分析：

**第一步——规则是什么（Rule）：**
- 中国《个人信息保护法》（PIPL，2021）第13、29条：处理敏感个人信息（包括生物特征）须有法律依据，通常须单独获取明确同意；数据处理须具有必要性。

**第二步——通俗解释（Plain English）：**
- 仅仅是为了方便或技术更新，不能强迫用户提交自己的生物特征数据。同意必须是真实、知情、自愿的。

**第三步——工程实践（Engineering Action）：**
- 提供多种验证方式选择（指纹、人脸、年票卡等）
- 就生物特征采集单独获取同意，并清楚说明用途
- 设置明确的数据保留期和删除机制
- 提供投诉和删除申请渠道
- 记录同意过程

**第四步——结论（Conclusion）：**
- 强制采集生物特征用于常规性服务（如动物园入园）不合法；在未取得必要性论证和明确同意的情况下存储数据违反PIPL。

| 角度 | 要点 |
|------|------|
| **核心原则** | 同意（consent）+ 必要性（necessity）+ 最小化（minimisation） |
| **生物特征特殊性** | 属于敏感个人信息，受更高级别保护 |
| **比较视角** | GDPR第9条同样对生物特征有更严格要求 |
| **工程师启示** | 技术上可行 ≠ 法律上允许；采集前必须论证必要性 |

## 案例十一：AI自动驾驶汽车（中国情境）

**来源：** Topic 5, Lecture 5, P.8（Slide 17）

### 案例内容

AI自动驾驶汽车的测试和部署，涉及安全性、测试要求、人工监督、事件报告和事故责任。

### PPT中的分析

> *"For AI vehicles, the legal question is not only 'does it work?' but 'is it safe enough, controlled enough, and documented well enough to be deployed?'"*

**主要法律关切：** 安全、测试、人工监督、事件报告、发生伤害时的责任。

**工程行动（Engineering action）：**
- 定义系统可以安全运行的范围
- 在真实条件和边缘案例中测试
- 保留事件/黑盒日志
- 监控软件和模型更新
- 在需要时提供回退和远程干预

**需保留的证据（Evidence to keep）：**
- 安全测试结果
- 更新和版本记录
- 事件日志
- 运营限制/部署条件
- 维护和监控记录

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **监管关注** | 技术可行性 vs 真实世界安全性 |
| **举证责任** | 需要文件证明：已充分测试；有记录；已部署监控 |
| **责任框架** | 中国：相关道路测试法规；EU：AI Act高风险；美：FAA/NHTSA等机构 |
| **持续义务** | 部署后持续监控；及时的更新和补丁是法律义务 |
| **工程师行动** | 系统日志 = 法律证据；完整记录 = 责任保护 |

## 案例十二：AI医疗系统（中国情境）

**来源：** Topic 5, Lecture 5, P.9（Slide 18）

### 案例内容

AI系统辅助诊断或治疗决策，涉及安全性、临床验证、人工监督、患者数据隐私和责任归属。

### PPT中的分析

> *"In healthcare, the question is not only whether AI is useful, but whether it is safe, explainable, supervised, and trustworthy enough for clinical use."*

**工程行动：**
- 部署前验证系统

- 明确何时需要人工审核

- 部署后监控错误、漂移和更新

**需保留的证据：**
- 验证和测试结果
- 子组性能记录
- 审计追踪/决策日志
- 患者数据访问日志
- 更新、监控和事件记录

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **安全验证** | 性能 ≠ 安全；需在真实临床人群中验证，而非仅在理想数据集上 |
| **临床监督** | 高风险决策须保持人工最终判断权（human-in-the-loop） |
| **隐私** | 医疗数据 = 最高敏感级别；需严格访问控制 |
| **可解释性** | 临床医生需要可理解的解释才能在临床决策中采用AI建议 |
| **漂移（Drift）** | 部署后模型性能可能下降，需持续监控 |

## 案例十三：Google高级技术外部顾问委员会（ATEAC）解散（2019）

**来源：** Topic 7, Lecture 7, P.7（Slide 16）

### 案例内容

Google于2019年成立了高级技术外部顾问委员会（Advanced Technology External Advisory Council，ATEAC），旨在监督AI开发并确保伦理原则的落实，但很快因其构成争议和规模化伦理实践的挑战而解散。

### PPT中的分析

> *"These boards often face difficulties, such as balancing business goals with ethical principles."*

背景：
- 许多大公司（Google、Microsoft、IBM）设立了AI伦理委员会（AI ethics boards）
- 目标：将公平性、透明度、可问责性、非歧视性整合进AI系统
- 挑战：在商业利益与伦理原则之间寻求平衡

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **自我监管局限** | 企业自设伦理委员会 = 自我监管（self-regulation），存在利益冲突 |
| **美国监管特点** | 美国无强制性AI法律 → 更依赖行业自律，但自律本身存在局限 |
| **与EU/中国对比** | EU AI Act和中国法规提供外部强制约束；美国自我监管更脆弱 |
| **伦理 vs 法律** | "伦理 = 应当（should）；法律 = 必须（must）" — 伦理无强制力 |
| **考试角度** | 说明为何单靠企业自律不足以管理AI风险，需要外部法律框架 |

## 案例十四：《通信规范法》第230条与AI内容审核

**来源：** Topic 7, Lecture 7, P.4（Slide 8）

### 案例内容

《通信规范法》（Communications Decency Act）第230条为网络平台提供了免于为第三方用户生成内容承担责任的豁免。随着AI越来越多地参与内容策展、审核和影响，出现了AI驱动的决策是否仍受第230条保护的争议。

### PPT中的分析

> *"As AI increasingly curates, moderates, and influences content online, questions arise about whether AI-driven decisions fall under the protections of Section 230."*

核心问题：
- 平台仅因免责条款享有保护，当AI主动干预内容时，这种免责是否仍然适用？
- AI内容策展是"中立平台行为"还是"主动编辑行为"？

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **美国法律特点** | 美国依赖现有法律（非专门AI法）来管理AI问题 |
| **平台责任边界** | 被动托管 vs 主动策展：AI介入后责任性质可能改变 |
| **消费者保护** | FTC关注：AI内容推荐是否构成不公平或欺骗性实践？ |
| **对比视角** | EU通过AI Act明确高风险推荐系统的义务；美国边界模糊 |
| **工程师启示** | 算法推荐系统可能引发法律责任，需透明度设计 |

## 案例十五：高频交易算法（High-Frequency Trading Algorithms）

**来源：** Topic 7, Lecture 7, P.6（Slide 15）

### 案例内容

金融服务领域的高频交易（high-frequency trading）算法存在可能破坏市场稳定或制造不公平交易环境的风险。NIST AI RMF将此作为AI风险管理在金融行业的示例。

### PPT中的分析

NIST AI RMF关注：
- 识别、管理和缓解AI技术带来的风险
- 强调在不同行业中负责任的AI开发与部署
- 对金融服务业的应用：管理高频交易算法对市场稳定性和公平性的潜在影响

### 考试分析角度

| 角度 | 要点 |
|------|------|
| **美国监管框架** | Dodd-Frank法案（金融透明度）+ CFPB（消费者金融保护）+ FCRA（信用信息） |
| **风险类型** | 技术风险（市场崩溃）+ 社会风险（系统性金融风险）+ 法律风险（市场操纵） |
| **速度问题** | AI决策速度远超人类监督能力 → 传统监管机制失效 |
| **自动化偏见** | 多个算法互相强化趋势 → 闪崩（flash crash）风险 |
| **NIST RMF应用** | 识别风险 → 分析 → 评估 → 处置，作为非强制性指南 |
| **工程师行动** | 熔断机制（circuit breakers）；速度限制；人工干预触发器 |

## 综合分析框架速查

### 通用案例分析步骤（考试必用）

```
第一步：识别系统类型
→ 输入是什么？输出是什么？是否从数据推断？是否自适应？影响什么决策？

第二步：识别风险类型
→ 技术风险 / 伦理风险 / 法律风险 / 社会风险（可能同时存在多种）

第三步：确定适用法律框架
→ 中国：PIPL / 网络安全法 / 数据安全法 / 算法推荐规定 / 深度合成规定 / 生成AI办法
→ EU：GDPR + EU AI Act（确定风险级别）
→ 美国：FTC法 / HIPAA / FCRA / COPPA / Dodd-Frank / CCPA

第四步：按四步方法作答
→ 规则（Rule）→ 通俗解释（Plain English）→ 工程实践（Action）→ 结论（Conclusion）

第五步：给出工程师建议
→ 具体的技术控制措施和文档要求
```

### 高频考察点对照

| 场景关键词 | 首要适用法律 | 核心义务 |
|-----------|------------|---------|
| 人脸识别 / 生物特征 | PIPL（中）/ GDPR（EU） | 同意 + 必要性 + 删除权 |
| 推荐系统 | 算法推荐规定（中）/ AI Act（EU） | 标注 + 解释 + 申诉 |
| 生成AI / 深度伪造 | 深度合成规定（中）/ AI Act Article 50（EU） | 标注 + 水印 + 内容管理 |
| 医疗AI | PIPL + 数据安全法（中）/ AI Act高风险（EU）/ HIPAA（美） | 验证 + 人工监督 + 审计 |
| 自动驾驶 | 中国道路测试法规 / AI Act高风险（EU）/ FAA/NHTSA（美） | 安全测试 + 日志 + 事件报告 |
| 招聘AI | PIPL（中）/ AI Act高风险（EU）/ FCRA + EEOC（美） | 无歧视 + 可解释性 + 审计 |
| 儿童平台 | 算法推荐规定（中）/ AI Act（EU）/ COPPA（美） | 年龄门 + 最小化 + 保护 |
| 金融AI | 数据安全法（中）/ EU AI Act / Dodd-Frank + FCRA（美） | 公平性 + 透明度 + 风险控制 |
